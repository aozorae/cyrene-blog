# 管理后台融合架构决策

- 状态：已确认
- 日期：2026-07-30
- 范围：第一阶段后台融合

## 背景

本项目是可供其他用户自行部署的开源博客。现有博客是 Astro 静态站点，现有管理后台是独立的 Cloudflare Worker，通过 GitHub API 修改博客仓库。

融合后的首要约束是：博客必须继续独立构建和部署。即使用户完全不部署管理后台，博客也应保持原有功能，并可部署到 Vercel、Netlify、GitHub Pages 或其他静态托管平台。

## 架构决策

### 仓库与部署单元

- 博客和后台保存在同一个 Git 仓库，不拆分成两个仓库。
- 博客继续位于仓库根目录，保留现有 `package.json`、构建命令和 `dist` 输出。
- 后台位于 `admin/`，拥有独立的 `package.json`、lockfile、Wrangler 配置、迁移和静态管理界面。
- 第一阶段不建立根 pnpm workspace，避免改变静态托管平台的安装和构建行为。
- 管理界面和管理 API 由同一个 Cloudflare Worker 提供，保持同源认证。
- 博客运行时不调用管理后台 API，也不读取 D1。

### 部署流程

- 后台只能通过 GitHub Actions 部署到 Cloudflare Workers。
- 后台部署 Action 同时支持首次手动运行和 `admin/**` 变更后的自动部署。
- 首次运行自动创建或查找 D1、执行迁移并部署 Worker。
- 后台目录的修改不应触发博客静态部署；博客内容和配置提交仍触发各静态托管平台自己的自动构建。
- 第一阶段不创建或绑定 R2、KV。

Action 所需的敏感信息保存在 GitHub Repository Secrets：

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
- `BLOG_GITHUB_PAT`
- `ADMIN_PASSWORD`
- `SESSION_SECRET`

后台首次打开时提供初始化界面，让用户填写要管理的 GitHub 仓库和分支。该设置保存在 D1，并使用 GitHub PAT 验证访问权限。项目不得包含作者个人的仓库、分支、Cloudflare 资源 ID 或部署域名等硬编码。

### 数据真源

- GitHub 仓库中的 Markdown、MDX 和配置文件是已发布内容的唯一真实来源。
- 浏览已发布文章、动态或配置时，后台实时读取 GitHub，不使用 D1 缓存替代 GitHub 内容。
- D1 只保存用户明确保存的草稿、后台自身设置、操作审计和必要的提交关联信息。
- 提交成功后，已提交草稿从待提交区移除；后续浏览重新读取 GitHub 版本。
- 后台只负责向 GitHub 提交。它不参与博客运行，也不直接部署博客。

### 草稿与提交

- 文章、动态和博客配置都支持保存草稿。
- 编辑界面提供清晰分离的“保存草稿”和“提交到 GitHub”操作。
- 单个编辑界面可以只提交当前内容。
- 后台提供统一的待提交列表，可以选择多个草稿或全选，并将所选变更合并为一个 GitHub commit。
- 提交成功后只提示“已经提交，自动部署”，并提供 commit 信息；不跟踪 Vercel、Netlify、GitHub Actions 等平台的最终部署状态。
- 删除已发布文章或动态时，二次确认后立即创建 GitHub 删除 commit，不进入草稿区。

### 并发冲突

- 草稿记录保存其基于的 GitHub 文件 SHA。
- 提交前重新读取 GitHub，并比较当前 SHA。
- 如果文件已被其他提交修改，后台明确提示冲突，默认不覆盖。
- 用户确认后可以强制覆盖；该操作必须在界面和审计记录中明确标识。
- 批量提交中存在未确认冲突时，不提交整批变更，避免只完成部分草稿。

### 内容范围

- 第一阶段支持 Markdown 文章的创建、完整读取、编辑、删除和嵌套路径。
- MDX 在后台列表中可见，但不通过表单编辑，用户应前往 GitHub 编辑带组件代码的 MDX。
- 文章表单包含标题、slug、摘要、分类、标签、正文、封面图片地址、发布时间和嵌套目录。
- 密码、许可证、作者覆盖、评论开关等高级 frontmatter 字段留待后续补充。
- 动态和配置沿用现有能力，并增加草稿与批量提交入口。

### 图片与 R2

- 第一阶段不提供文件上传。
- Markdown 图片和封面图片由用户填写普通 URL 或使用仓库原有的相对路径。
- R2 上传是后续可选功能，默认关闭。未来启用时需要独立的激活流程、公开地址配置和资源生命周期设计。
- 未来的草稿图片可以在草稿阶段删除并同步删除 R2 对象；已发布图片不随文章删除自动清理。

### 认证与安全

- 第一阶段保持单管理员模型。
- 管理 UI 和 API 保持同一个 Worker 域名，不开放跨域管理接口。
- 管理密码和会话签名密钥必须分离。
- 补充登录限流、请求来源校验、输入校验和审计记录。
- GitHub PAT 使用只覆盖目标仓库所需的最小权限，不得写入仓库文件或日志。

## 领域术语

| 术语 | 定义 |
| --- | --- |
| 已发布内容 | 当前存在于目标 GitHub 分支中的 Markdown、MDX 或配置文件。 |
| GitHub 真源 | 已发布内容始终以 GitHub 当前文件为准，D1 不保存可替代它的发布副本。 |
| 草稿 | 用户主动保存到 D1、尚未提交或包含新修改的内容。 |
| 待提交项 | 可被单独选择或加入批量 GitHub commit 的草稿。 |
| 当前提交 | 只提交当前编辑器中的一项草稿。 |
| 批量提交 | 将选中的文章、动态和配置草稿合并为一个 GitHub commit。 |
| 基准 SHA | 创建或更新草稿时对应的 GitHub 文件版本，用于发现并发修改。 |
| 强制覆盖 | 用户在获知 SHA 冲突后，明确允许以草稿内容覆盖 GitHub 最新文件。 |
| 后台设置 | 目标仓库、目标分支等仅供管理 Worker 使用并存储于 D1 的设置。 |
| 博客配置 | `src/config` 等需要提交到 GitHub、由静态博客构建读取的配置。 |
| 自动部署 | GitHub 收到提交后，由用户选择的静态托管平台自行检测并构建；后台不追踪其完成状态。 |

## 第一阶段不做

- 不重做现有后台视觉设计。
- 不引入多用户、角色权限或 OAuth。
- 不追踪各静态托管平台的部署状态。
- 不启用 R2、KV 或文件上传。
- 不把博客改成依赖 Worker、D1 或后台 API 的动态应用。
- 不提供完整 MDX 可视化编辑器。
- 不一次性覆盖所有高级文章字段。

## 实施顺序

1. 将现有后台迁入 `admin/`，移除个人硬编码，并保持博客根构建不变。
2. 增加后台部署 Action、D1 自动初始化和首次仓库配置。
3. 建立草稿、后台设置和审计数据模型。
4. 补齐文章完整读取、编辑、嵌套路径和冲突处理。
5. 为文章、动态和配置增加保存草稿、当前提交和批量提交。
6. 补齐单管理员认证安全与输入校验。
7. 验证博客静态构建以及后台 Worker 的独立检查和部署流程。
